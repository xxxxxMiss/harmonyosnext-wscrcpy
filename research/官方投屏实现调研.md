# DevEco Testing 投屏 / 录制实现方式调研

> 调研目标：搞清 HarmonyOS 官方工具（DevEco Testing / Hypium）为什么能在**动画场景下流畅**投屏，而我们的"连拍截图"路线（`snapshot_display` 循环）做不到。
>
> 调研方式：**本地逆向**（DevEco Testing 26.0.0.500 安装包 + DevEco Testing 运行日志）+ **真机实证**（BRA-AL00 / HarmonyOS 6.1.1.120 / uitest 6.0.2.3）+ 官方文档/开源仓库交叉验证。
>
> 调研时间：2026-09-14
> 结论状态：**官方实现方式已完全还原到 API 与符号级**；复用路径的兼容缺口已定位到 2 个符号。

---

## 0. 一句话结论

官方**从来不用截图**。它走的是 **Render Service 虚拟屏（Virtual Screen）→ 硬件编码器 Surface → H.264 码流**的零拷贝管线：让渲染服务把屏幕内容**直接合成进编码器的输入 Surface**，全程没有 RGBA→JPEG 的软件转换、没有落盘、没有文件传输。

我们路线的 1.58 fps 不是 hdc 慢，而是 `snapshot_display` 每帧都要在 CPU 上做 `RGBA8888 → RGB888 → JPEG` —— 真机日志里就是这么打的：

```text
snapshot: convert rgba8888 to rgb888 successfully.
```

动画场景下这条路**原理上**就不可能流畅。

## 1. 我们路线 vs 官方路线

| | 我们的连拍截图路线 | 官方（DevEco Testing）路线 |
|---|---|---|
| 采集入口 | `snapshot_display -f x.jpeg`（一次性进程） | `Rosen::ScreenManager::CreateVirtualScreen()` 常驻 |
| 合成来源 | 每帧重新 `GetScreenSnapshot` 截一次全屏 | RSS 持续把物理屏内容 mirror 到虚拟屏 |
| 帧格式 | RGBA8888 → RGB888 → **JPEG（CPU 软编）** | **GPU 合成直写编码器 Surface**（不落 CPU） |
| 传输格式 | JPEG 文件（~230KB/帧）+ hdc file recv | **H.264 码流**（gRPC 流式，增量帧） |
| 驱动方式 | PC 触发一次 → 等文件 → 拉取（串行 RTT） | 设备侧推流，PC 只消费（异步） |
| 实测帧率 | **1.58 fps** | 官方日志显示可持续拉流 27 分钟；社区称"基本持平真机帧率" |

**关键差异**：截图路线的成本是 `合成 + 软件编码 + 落盘 + 传输`；虚拟屏路线只剩 `传输`。

## 2. 官方实现架构（四层）

```text
┌────────────────────────── PC (macOS) ──────────────────────────┐
│ DevEco Testing GUI (Electron)                                  │
│   └─ Java 服务层：screenCastingResource.jar（联网下载的资源包）  │
│        · 起本地 WebSocket 服务 :8710 供渲染层取流                │
│        · 起 gRPC client                                          │
│   └─ Python 层：devicetest/controllers/tools/recorder/          │
│        · RecordAgent → 起设备侧 daemon / fport / 上传 so          │
│        · RpcManager → gRPC 调 onStart / onEnd / onRequestIDRFrame │
└───────────────┬────────────────────────────────────────────────┘
                │ hdc fport tcp:<port> → tcp:5001（或 localabstract）
┌───────────────▼──────────── 设备侧 ─────────────────────────────┐
│ /system/bin/uitest start-daemon singleness                      │
│   --extension-name libscreen_recorder.z.so -p 5001 -m 1         │
│   -screenId 0                                                    │
│   └─ dlopen(/data/local/tmp/libscreen_recorder.z.so)            │
│        · gRPC Server（ScrcpyService）                            │
│        · ScreenRecorder / ScreenEncoder（native_screen_encoder.cpp）│
│        · Rosen ScreenManager → 虚拟屏 + 镜像                       │
│        · OH_VideoEncoder(AVC, Surface 模式) → H.264               │
│        · OH_AVMuxer → /data/local/tmp/mytest.mp4                 │
└──────────────────────────────────────────────────────────────────┘
```

要点：

1. **设备侧不是独立进程**，而是 `uitest` 用 `dlopen` 加载的插件（extension）。设备侧能力来自 `uitest` 这个 shell 身份进程，所以不需要应用签名。
2. **依赖 shell 的 `/data/local/tmp`**：so 放这里，`uitest` 只从固定路径加载（`extensionPath = /data/local/tmp/ + name`）。
3. **PC 侧不解析视频**，只做转发/落盘；真正的解码渲染在 Java/Electron 层。

## 3. 设备侧核心实现（符号级）

### 3.1 采集：RSS 虚拟屏，不是 AVScreenCapture

从 `libscrcpy_server*.z.so` 的动态符号表还原（源码文件名为 `native_screen_encoder.cpp`）：

| 调用 | 作用 |
|---|---|
| `Rosen::DisplayManager::GetDefaultDisplayId()` | 取默认物理屏 |
| `Rosen::DisplayManager::GetDisplayByScreen(screenId)` | 按 screenId 取 Display（拿 `GetWidth/GetHeight/GetDpi`） |
| `Rosen::ScreenManager::CreateVirtualScreen(VirtualScreenOption)` | **创建虚拟屏**，返回 virtualScreenId |
| `Rosen::ScreenManager::SetVirtualScreenSurface(id, sptr<Surface>)` | **把编码器的输入 Surface 挂上去**（零拷贝关键） |
| `Rosen::ScreenManager::SetVirtualScreenRefreshRate(id, fps)` | 设定虚拟屏刷新率，决定上限帧率 |
| `Rosen::ScreenManager::SetVirtualMirrorScreenCanvasRotation(id, bool)` | 镜像画面旋转 |
| `Rosen::ScreenManager::SetVirtualScreenSecurityExemption(id, type, vector)` | 安全豁免（否则隐私窗口会被打码/剔除） |
| `Rosen::ScreenManager::MakeMirror(mainScreenId, {virtualScreenId}, mirrorId)` | **把物理屏镜像到虚拟屏** |
| `Rosen::ScreenManager::RegisterScreenListener(...)` | 监听屏幕变化，自动重启 ScreenCopy |
| `Rosen::ScreenManager::DestroyVirtualScreen(id)` | 销毁（**就是这一个符号在 6.1 上不兼容，见 §5**） |

对应的设备侧日志字符串（证实运行时的完整流程）：

```text
%{public}s Invoke StartScreenCopy....
%{public}s create virtual screen failed.
%{public}s set virtual screen surface failed.
%{public}s set virtual screen refresh frame rate failed.
%{public}s set virtual screen skip privacy windows failed.
%{public}s Screen changed, auto restart ScreenCopy
%{public}s Finish StopScreenCopy...., frame_count: %{public}d
%{public}s frameBitRate:  %{public}ld.
%{public}s frameRefreshInterval:  %{public}d.
%{public}s first encode output
```

> `VirtualScreenOption` 的字段可以从 `libdm.z.so` 的 `CreateVirtualScreen` 使用点反推：`name` / `width` / `height` / `density` / `surface` / `mirrorScreenId` / `flags`。
>
> **这正是系统自带录屏（AOD/截屏录屏）走的那条路** —— 官方把系统能力"借"给了 uitest 插件。

### 3.2 编码与封装：公开 NDK API

```text
OH_VideoEncoder_CreateByMime(OH_AVCODEC_MIMETYPE_VIDEO_AVC)
  → OH_VideoEncoder_Configure(OH_AVFormat)     # OH_MD_KEY_WIDTH/HEIGHT/FRAME_RATE/BITRATE/
  → OH_VideoEncoder_GetSurface()               # 拿到输入 Surface → 交给虚拟屏
  → OH_VideoEncoder_Prepare / Start
  → OH_VideoEncoder_SetCallback(OnStreamChanged/OnNeedInputBuffer/OnNewOutputBuffer)
  → OH_VideoEncoder_SetParameter(OH_MD_KEY_REQUEST_I_FRAME)   # 对应 gRPC onRequestIDRFrame
  → OH_VideoEncoder_FreeOutputData / NotifyEndOfStream / Stop / Destroy

OH_AVMuxer_Create(fd, MP4) → OH_AVMuxer_AddTrack → OH_AVMuxer_WriteSample → Stop/Destroy
```

这两块都是**公开 NDK API**（`libnative_media_venc.so` / `libnative_media_avmuxer.so`），第三方可以直接用。**难点只在采集端（虚拟屏）**。

### 3.3 控制协议：gRPC

proto 定义（从 `scrcpy.proto` 的序列化描述符还原）：

```proto
service ScrcpyService {
  rpc onStart(Empty) returns (stream ReplyMessage);   // 服务端流式回传帧
  rpc onEnd(Empty) returns (ReplyEndMessage);         // 返回 result = 帧数
  rpc onRequestIDRFrame(Empty) returns (ReplyEndMessage); // 请求关键帧
}
message ReplyMessage {
  string data = 1;                       // 帧数据
  int32  reply_type = 2;
  map<string, ParamValue> payload = 3;
}
message ParamValue {  // oneof
  int64 val_int = 1; double val_double = 2; string val_string = 3;
  bool val_bool = 4; bytes val_bytes = 5; float val_float = 6;
}
```

PC 侧客户端（`rpc_manager.py`）关键参数：`grpc_max_receive_message_length = 10485760`（10MB）。

### 3.4 传输通道

```python
# record_agent.py 关键行
"/system/bin/uitest start-daemon singleness --extension-name libscreen_recorder.z.so -p 5001 -m 1 -screenId 0"
hdc fport tcp:<localPort> tcp:5001                       # 普通设备
hdc fport tcp:<localPort> localabstract:screen_record_grpc_socket   # 新版设备
```

设备侧进程识别特征：`ps -ef | grep singleness` 中出现 `extension-name` + `libscreen_recorder`。

## 4. 版本演进：4 个 so 变体

安装包内自带 4 个互斥变体，运行时逐个试（`_start_scrcpy_server` 的 `os.walk` 循环），**全部失败则回退截图**。
文件名里带 `unix` 的走 `localabstract`，不带的走 TCP；两者都会先改名为 `libscreen_recorder.z.so`。

| so | 大小 | md5 | NEEDED | 定位 |
|---|---|---|---|---|
| `libscrcpy_server1.z.so` | 3,041,461 | `b067813b…` | 16 | grpc 静态链全量版；与设备上遗留的 `libscreen_recorder.z.so` **同 md5** |
| `libscrcpy_server2.z.so` | 309,430 | `474ba825…` | 15 | protobuf 动态链接版（带 audio capturer） |
| `libscrcpy_server3.z.so` | 288,950 | `0b4e4e5a…` | 20 | 中间版本 |
| `libscrcpy_server4.z.so` | 264,374 | `fa0cefa7…` | 15 | **依赖最少、最新**，是首选基线 |

> 注意：DevEco Testing 会在真机上**优先复用已存在的** `/data/local/tmp/libscreen_recorder.z.so`（"Using device recorder so start success"），只有失败才推内置变体。

## 5. 真机实证结果（关键）

### 5.1 环境

| 项 | 值 |
|---|---|
| 设备 | BRA-AL00（真机，非模拟器） |
| 系统 | `6.1.0.135(SP8C00E120R4P11)` / `OpenHarmony-6.1.1.120` |
| ABI | aarch64 |
| uitest | **6.0.2.3**（官方要求 ≥ `4.1.4.6`，`check_uitest_version` 通过） |
| shell 身份 | `uid=2000(shell) context=u:r:sh:s0`（非 root） |
| `localabstract` 支持 | ❌ 不支持 → 只能走 `fport tcp:` |
| 设备上已有的 so | `/data/local/tmp/libscreen_recorder.z.so`（3MB，md5 与变体1 一致）、`libscreen_casting.z.so`、`caught.so`（**均为上一轮会话遗留，非系统自带**） |

### 5.2 4 个变体全部加载失败 —— 原因不是"缺库"，是**版本 ABI 漂移**

逐个 push + `uitest start-daemon` 实测：

| 变体 | dlopen 结果 | 失败符号 |
|---|---|---|
| 1 | ❌ | `absl::lts_20220623::Mutex::~Mutex()` |
| 2 | ❌ | `protobuf::internal::ArenaStringPtr::Set(EmptyDefault, string&&, Arena*)` |
| 3 | ❌ | 同上（protobuf） |
| 4 | ❌ | `Rosen::ScreenManager::DestroyVirtualScreen(unsigned long)` |

**根因**：设备上这套库是 **HarmonyOS 6.1.1 的版本**，而 DevEco Testing 26.0.0.500 内置 so 是按另一批次（absl 20220623 / 20230802、旧版 protobuf）编的。两侧都"有库"，只是**符号版本对不上**。

### 5.3 好消息：缺口极小，只有 **2 个符号**

把 4 个变体的未定义符号与**设备实际导出的符号全集**（libdm / libprotobuf / libgrpc / libgrpcxx / libabsl_sync / libnative_media_* / libsurface / libutils / libc / libc++ / libhilog，共 13,304 个）做差集：

| 变体 | 缺失符号数 | 其中真正需要处理的 |
|---|---|---|
| 1 | 204 | grpc/absl 大批量（静态链接全量版，最不兼容） |
| 2 | 68 | protobuf 老版 ABI + absl 20230802 + 2 个已知点 |
| 3 | 67 | 同上 |
| **4** | **43** | **实际只有 2 个**（其余 `__cxa_* / __register_frame_info` 由 libc++ 提供，`OH_VideoEncoder_*` 已确认设备 `libnative_media_venc.so` 里有，`gpr_* / RefBase::*` 由 libgpr/libutils 提供） |

变体 4 的**真实**兼容缺口：

```text
1) OHOS::Rosen::ScreenManager::DestroyVirtualScreen(unsigned long)
      → 设备 libdm.z.so 只有 (unsigned long, bool) 两参版
2) OHOS::AudioStandard::AudioCapturer::Create(...)@1.0
      → 设备侧带版本标记；且录屏不需要音频，可直接 stub
```

已确认可用的设备侧依赖：

```text
> nm -D libnative_media_venc.so | grep OH_VideoEncoder_GetSurface
0000000000006200 T OH_VideoEncoder_GetSurface
0000000000006c64 T OH_VideoEncoder_SetCallback
```

**也就是说：给变体 4 打一个"两参版 DestroyVirtualScreen + AudioCapturer stub"的垫片（shim），就有很大概率直接跑起来。**

## 6. 顺带确认的两条"其他官方路线"

### 6.1 Hypium 插件路线（`agent.so` + 自定义 RPC）

社区已完整逆向（[testerhome: 鸿蒙投屏实现](https://testerhome.com/topics/42029)）：

```text
1) push agent.so → /data/local/tmp/
2) uitest start-daemon singleness --extension-name agent.so
3) hdc fport tcp:<p> tcp:8012
4) 走自定义 RPC 协议：
   帧头 _uitestkit_rpc_message_head_ … 帧尾 _uitestkit_rpc_message_tail_
   （中间 4B 请求 id + 4B 长度）
5) 业务调用：
   {"module":"com.ohos.devicetest.hypiumApiHelper","method":"Captures",
    "params":{"api":"startCaptureScreen","args":{"options":{"scale":0.5}}}}
6) 服务端在画面变化时回传一系列 JPEG 帧
```

即：**JPEG 流 + 变化触发**。比"PC 逐帧拉截图"好得多（异步推、只在变化时发），但仍是 JPEG 软编。这是 **Hypium IDE 插件自带投屏**的实现，不是 DevEco Testing 主推流。
> `uitest` 的 extension 加载点已开源可查：[testfwk_arkxtest](https://gitee.com/openharmony/testfwk_arkxtest)。

### 6.2 权限模型（为什么第三方 App 走不通）

真机 hilog 实测 `snapshot_display`：

```text
E C05A01/foundation/ATM: [VerifyAccessToken]PermissionName(ohos.permission.CUSTOM_SCREEN_RECORDING) is not exist.
E .../snapshot_display/IPCObjectProxy: ... error:29201 desc:(subErr:4 SubErrDesc:outer:operation not permitted)
```

- `snapshot_display` 最终仍能成功（走的是 DMS 的截图通道，权限报错是 fallback 噪音），但**能力受系统管控**。
- 应用侧公开 API `OH_AVScreenCapture`（NDK，`native_avscreen_capture.h`，公开 SDK 里有头文件）需要 **`ohos.permission.CUSTOM_SCREEN_RECORDING`** —— 这是 **system_basic / 受限权限**，三方应用拿不到。
- 而**虚拟屏路径（`Rosen::ScreenManager`）不经过该权限校验**，所以官方 so 能在 shell 身份下跑通。

> 这解释了为什么"手表上 `AVScreenCaptureRecorder` 不支持"—— 不是设备不支持，而是**这条路本来就不是给三方应用走的**。

### 6.3 DevEco Studio 本身没有投屏

`DevEco Studio 6.1.1.300` 的 `plugins/` 下无 cast / mirror / scrcpy 相关插件。投屏能力**只在 DevEco Testing 侧**，且其核心资源 `screenCastingResource.jar` 是**联网下载 + 鉴权**的（`https://devecotesting.huawei.com/ts/api/v2/common-resource-files/930`，直接 curl 返回 401）。
运行日志证实这条管线在**本机真机上确实跑通过**：

```text
[VideoRecordCasting] Server started!
[VideoRecordCasting] start video cast, sn is 9CN0224A11000514
[VideoRecordCasting] startCaptureScreen onReady
[VideoRecordCasting] 获取视频流失败UNAVAILABLE: Network closed for unknown reason   ← 27 分钟后断流
```

## 7. 对我们的启示（可落地路线）

### 路线 A：复用官方 so + 符号垫片（验证最快，1~2 天）

1. 取变体 4，给 `DestroyVirtualScreen(ulong)` 打补丁（改成两参版传 `false`），或做一个 `LD_PRELOAD` 垫片提供该符号 + `AudioCapturer::Create` stub。
2. `push` + `uitest start-daemon` + `hdc fport`，PC 侧写 gRPC 客户端，先只做**帧率实测**，验证"动画场景是否真的流畅"。
3. 预期：能拿到 30~60fps 的 H.264 流。

**优点**：不写设备侧代码，能最快拿到"官方级流畅度"的实测数据。
**风险**：官方 so 不可再分发；随 HarmonyOS 版本升级会再次 ABI 漂移。

### 路线 B：自研设备侧 daemon（推荐长期方案）

采集仍然必须借虚拟屏（三方拿不到 `CUSTOM_SCREEN_RECORDING`），但**编码/封装/传输全用自己的代码**：

| 模块 | 方案 | 许可 |
|---|---|---|
| 虚拟屏采集 | `Rosen::ScreenManager`（同官方）或 `OH_AVScreenCapture`（若有系统签名） | 平台符号 |
| 编码 | `OH_VideoEncoder_*`（AVC/HEVC，Surface 模式） | **公开 NDK** |
| 封装 | `OH_AVMuxer_*`（MP4）或**干脆不封装，直接吐 Annex-B/AVCC** | **公开 NDK** |
| 传输 | 自定义（TCP over `hdc fport` / localabstract），帧头带 PTS + IDR 标志 | 自研 |
| 宿主 | `uitest start-daemon` extension（复用官方加载机制） | 依赖 uitest |

**关键设计点**：投屏场景**不要封装 MP4**——直接发裸 H.264，PC 侧用 `ffmpeg`/硬解解码，能再省一层延迟。录像场景再落 MP4。

### 路线 C：Hypium `agent.so` 协议（次优）

直接实现 `_uitestkit_rpc_message_*` 协议 + `startCaptureScreen`，拿 JPEG 流。**比截图强、比 H.264 弱**，且 `agent.so` 仍要来自 Hypium 插件（鉴权同样受限）。
